## Goal

The sentinels and exceptions of the core, with the same error codes in both languages, so the root cause is never lost.

## Design notes

- CLAUDE.md: sentinels live in `application/errors.go` and `domain/errors.go` and are composed with `errors.Join`, so a caller can test the root cause with `errors.Is`. The old library has the same shape in its own `errors.go` files (read, not edited).
- Python: an exception hierarchy with one base class for the library and subclasses per layer; a chained cause (`raise ... from ...`) keeps the root cause, the same role as `errors.Join` (Q07-8: PEP 8 and the Go layers).
- Codes come from `contracts/errors/` (T-02.3) through the generated code of T-02.4. REQ-CNF-004: the validation and configuration codes are identical; the message text may differ. Each error carries its code, the field or event type involved and no value (the value may be a secret).
- The hot path never throws (ADR-005, REQ-DLV-002): these errors are returned as values by the services and raised only by construction and start (invalid configuration, REQ-CFG-002). Say so in the doc comment of each.
- Error translation of an adapter stays in the adapter's `error/` folder (CLAUDE.md); this task defines only the sentinels of the domain and application layers.
- Open question to the maintainer: whether the generated code owns the sentinels (one per catalog code) or the hand-written layer files wrap them. Default: the generated file defines the codes; `errors.go` and `errors.py` define the sentinels and map them by code.
- Go exported identifiers have doc comments that start with their own name (`go doc` rule of CLAUDE.md).

## Acceptance criteria

- Every code of the catalog that a core layer can produce has a sentinel (Go) and an exception class (Python), with the same code string.
- `errors.Is` finds the root cause through a join of two sentinels; in Python the cause is reachable through the chain.
- No error message contains a value passed by the caller, proven by a test with a sentinel-looking secret.
- A test lists the codes of both languages from the shared fixture and compares them.
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

Black-box tests in both languages; the shared codes table compared by a small test in each language.
