## Goal

One validated configuration model shared by both languages, with the base profiles as functions, and no reading of the environment or of a file.

## Design notes

- REQ-CFG-001 to REQ-CFG-005 and Q06-3: ADR-004 stays. The library never reads the environment or a file; `Config` carries the env tags as documentation for the consumer, who loads it with its own tool and passes the values in. Precedence, lowest to highest: defaults, then the profile, then the options given in code.
- Validation at start with an error that names the field and the reason (REQ-CFG-002); the error code comes from the catalog of T-02.3 and is identical in both languages (REQ-CNF-004). Several problems are reported together, not one at a time.
- Profiles are functions that return a configuration: `microservice` (delivery mode `best_effort`), `cronjob` and `worker` (`retry`), `robotics` and `offline_device` (`durable`) (REQ-CFG-004). They are only defaults and can be overridden. The delivery modes are used by T-05 and T-06; this task defines the field and the validation, not the behavior. Whether `durable` can be chosen before the spool exists is a question: proposed answer, validation accepts it and the composition root refuses to start a `durable` destination without a `LocalSpoolPort` (T-03.9). Awaiting the maintainer.
- Defaults of PR-001: queue 10,000 events, batch 100, flush every 2 s, timeout 3 s; the limits of T-03.5; spool quota 256 MiB per destination (Q03-5, Q07-11).
- The configuration schema is generated from `contracts/` by T-02.4 (REQ-CNF-002). The model here is the hand-written domain type that the generated schema describes; a test checks that every field of the schema exists in the model and the reverse.
- The configuration carries only the settings of each adapter, never an adapter name (REQ-ARC-013). The old `TelemetryConfig` (`internal/logging/infrastructure/config`) and its tags are read for field names that must survive (host, port, level) and their `.env.example` rows are kept until T-04.7.
- No secret has a default; REQ-CFG-005.

## Acceptance criteria

- No code of the library calls `os.Getenv`, `os.environ`, `envconfig` or reads a file (a test greps the sources, in both languages).
- An invalid configuration fails at start with the field name and the reason, and with the same code in Go and Python.
- Each profile returns the delivery mode of REQ-CFG-004; an option in code overrides the profile, which overrides the default.
- The test of the env tags lists every tag and fails if one is added without a documented row.
- Ends with the checks of the README section 3 green in every language the task names.

## Notes

**Done 2026-10-30** (Go 1.25.5, Python 3.11.1). The coordinator wrote the contract first (the schema, the `delivery_mode` enum, regenerated the code), the table of variables, `.env.example` and 23 shared cases computed with a reference model in Node.js; two agents wrote the code in parallel; the coordinator verified independently and wrote the documents.

- **Built.** The configuration schema (`contracts/config/config.schema.json`, with an `x-env` name on every property) and the enum `delivery_mode` (generated `DeliveryMode` in both languages); the model (`Config`), `Defaults`, the five profiles, `Validate` / `validate_config`, `ValidationError` / `ConfigurationError` with the list of problems, and `ConfigurationProvider` (the `ConfigurationPort`, which also generates the instance id); `Configuration` now holds the resource, the delivery settings, the limits, the spool settings and the masking options. See section 2.14 of the architecture document.
- **The shared cases.** 23 files in `integration-tests/fixtures/config/` (9 valid, 14 invalid): each profile, precedence, every field set, masking options, each rule of the validation, and several problems together. The valid ones compare the exact canonical JSON of the effective configuration; the invalid ones the exact list of fields and codes. All pass in Go and Python with no edit of any fixture; one expected value changed on purpose (`microservice_minimal`) made both fail, restored both pass. The table of variables and `.env.example` were written before the code and a test in each language keeps the schema, the code, the table and `.env.example` equal.
- **Verification.** Go: `gofmt` and `goimports` clean, vet and build clean, all tests pass (architecture included), coverage **98.9%**; the generator was re-run and produced no change. Python: `ruff` clean, **282 tests**, coverage **100%**. The registry: `REQ-ARC-007`, `REQ-CFG-001`, `REQ-CFG-002`, `REQ-CFG-003` and `REQ-CFG-004` have tests (26 of 130 covered, 96 pending, 8 without a task).
- **Open question, decided with the default.** `durable` is accepted by the validation (with a spool directory); the composition root (T-03.9) refuses to start a durable destination without a spool port. The maintainer was not asked.
- **Choices.** The env tags have no `default=` (see ADR-004). Times are integers in milliseconds. A zero value is invalid, so the zero `Config` is not usable: start from a profile. A profile changes only the delivery mode. A whitespace-only spool directory counts as set in both languages. The validation reports each field once and relation rules (batch not above queue, batch limit not below event limit) only when both operands are valid. The names `TELEMETRY_*` replace the old `LOGGER_*` for the new core; the old ones stay until T-04.7.
- **Known gaps.** **REQ-CNF-002 asks for the configuration schema to be generated into code and this model is hand-written and checked by a test**: the requirement is moved to unassigned until the maintainer decides to generate it or to accept the checked model. A consumer's extra pattern that is valid in one regular expression engine and not in the other is rejected only in the engine that cannot compile it. The consumer-side loading (an environment loader) is the consumer's; the core has none. `REQ-CFG-005` is checked by the security checklist (T-13.3), not by a test of the repository content.
