## Goal

Apply the size limits to attributes, to the whole event and to an HTTP batch, with a documented policy and a count of what was cut.

## Design notes

- Defaults of Q08-9 and REQ-CTR-010, REQ-SEC-004, all configurable: attributes 32 keys, key 64 characters, value 256 characters; event 64 KiB; HTTP batch 1 MiB. Today's library has no such limits, so nothing here is migrated.
- Policy (REQ-CTR-010): excesses are truncated or dropped by a documented rule and counted in diagnostics. Proposed rule, to confirm with the maintainer before it is written into the contract: a value longer than the limit is truncated and a key longer than the limit is truncated; keys beyond the 32nd are dropped in the order they were given; an event over 64 KiB after the cuts is rejected with a classified error and counted (a truncated half-event is not useful). Awaiting the maintainer on the last point.
- Count in characters, not bytes, for keys and values; count bytes of the canonical JSON (T-02.5) for the event and the batch, because that is what leaves the process. Go and Python count the same way (a fixture with multi-byte characters proves it).
- The batch limit is checked where batches are built (T-04.4, T-05.1); this task defines the limit as a value and a pure function `fits_in_batch`, not the batcher.
- The counters are plain values returned with the result of the call; exposing them as diagnostics belongs to T-05.5. Never log or count the cut value (it may be sensitive).
- Truncation runs after masking, so a secret cut in half is never half-visible (the order of T-03.3).

## Acceptance criteria

- An attribute value of 256 characters is kept; 257 is truncated to 256 and counted; the 33rd key is dropped and counted.
- An event of exactly 64 KiB in canonical JSON is accepted; one byte more is rejected with the code of T-02.3 and counted.
- The defaults are exactly those of Q08-9 and each is overridable by configuration.
- Go and Python give identical results and counts on the shared cases table.
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

Boundary tests in both languages over the shared cases; a test that the counters never contain the cut text.

## Notes

**Done 2026-10-30** (Go 1.25.5, Python 3.11.1). Two agents wrote the code in parallel after the coordinator prepared the shared cases; the coordinator verified independently and wrote the documents.

- **Built.** `Limits` (value object), `ApplyLimits` and `fits_in_batch` (domain operation, its own package `operations/limits`), `LimitsService` (application), in both languages. The policy is in section 2.13 of the architecture document.
- **The shared cases.** 22 files in `integration-tests/fixtures/limits/`, with the expected values computed by a **reference algorithm written in Node.js** from the rules of the task (independent of both implementations): the boundaries (256 and 257 characters, 64 and 65, 32 and 33 keys, exactly 65536 bytes and one more), characters versus bytes (emoji and 2-byte characters), key collisions after the cut, lists, custom limits, invalid limits and the batch table. All pass in Go and in Python with no edit of any fixture. One expected value changed on purpose (`thirty_three_keys`) made both languages fail; restored, both pass.
- **A differential test beyond the cases.** 8000 random envelopes (attributes with keys and values made of ASCII, accented, euro, emoji and other astral characters, lists, numbers; small limits so that cuts and rejections are frequent: 6741 with cuts, 754 rejected) went through the Go service and the Python service. **0 differences** in the limited envelope, the counters and the error code.
- **Verification.** Go: `gofmt` and `goimports` clean, vet and build clean, all tests pass (architecture included), coverage **99.0%**. Python: `ruff` clean, **251 tests**, coverage **100%**. The registry: `REQ-CTR-010` and `REQ-SEC-004` have tests (21 of 130 covered, 101 pending, 8 without a task).
- **Open question, decided with the default.** An event that is over 64 KiB after the cuts is **rejected**, never cut (the task asked to confirm it with the maintainer; the maintainer was not asked). If a truncated event is preferred, `ApplyLimits` changes and the cases of the size.
- **Choices.** The keys are limited in the sorted order of the canonical form, not in the order they were given, because a Go map has no order; the task proposed "the order given", so this is a deviation to confirm. A key that collides after the cut is dropped. The canonical JSON package exports its key order (`KeyLess` in Go, `utf16_sort_key` in Python) so it is written once. A bool is never cut in Python. `NewLimits` also refuses a batch limit below the event limit.
- **Known gaps.** The payload limit of REQ-SEC-004 (`data` alone) has no default in the specification and is not applied separately: the event limit covers it. A Python key with a lone surrogate makes the service return `EnvelopeLimitsFailedError` (it has no canonical form). The batch limit is a value and a function; the batcher is T-04.4 and T-05.1. The counters are returned with the result; the diagnostics are T-05.5. The limits come from the configuration in T-03.6.
