## Goal

Mask every event once, before any sink, with the detectors of ADR-006 plus the default list of REQ-SEC-002, in both languages.

## Design notes

- Migrate, do not rewrite from memory: the old detectors live in `internal/logging/domain/operations` (AWS access keys, bearer credentials, connection-string passwords, credential pairs, JWTs, private key blocks, sensitive field names, the masker and the replacement text). Read them and port the behavior, with their tests, to the new domain. Nothing is removed (Q06-5).
- New in REQ-SEC-001 to REQ-SEC-003: redaction configurable by field name and by pattern, the default list (`password`, `token`, `authorization`, `api_key`, `secret`), and an optional classification per field with a rule per class (drop, redact, allow). Where the fields come from: the consumer's configuration (T-03.6), never a file or the environment.
- Scope: the masker walks `data`, `attributes` and `context` of the envelope, not only the message. The replacement text of today is `*****MASKED*****`; keep it identical in both languages and in the contract.
- ADR-006: the whole entry is masked once, in the service, before it reaches any sink; the sinks never see sensitive data; adding a sink cannot reopen the leak. A test proves that no code path logs an entry unmasked (CLAUDE.md).
- Python uses the same patterns. Regular expression engines differ (Go RE2 has no look-around); write the patterns in the common subset and test the same table of inputs in both languages. A pattern that cannot be expressed in both is a question to the maintainer.
- Known limits of ADR-006 stay documented: free text with an unusual secret is not recognized until the consumer adds a pattern; the names `body`, `content` and `payload` are always hidden (check that the rule survives in the new envelope, where `data` is typed: open question for the maintainer).
- Masking never changes the event type, the ids or the times, and it never fails the call (ADR-005).

## Acceptance criteria

- Every detector of the old library gives the same result on its old test inputs in the new code.
- A field named like an entry of the default list, in any depth of `data` or `attributes`, is masked; with a classification rule `drop` the field is removed.
- Go and Python produce identical output on the shared cases table.
- A test with a spying sink proves the sink never receives an unmasked secret, whatever the capability.
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

Ported unit tests of each detector; the shared cases table in both languages; the spying-sink test; a review that no code path reaches a sink without the masking service.

## Notes

**Done 2026-10-30** (Go 1.25.5, Python 3.11.1). Two agents wrote the code in parallel after the coordinator prepared the shared tables; the coordinator verified independently and wrote the documents. A session limit stopped both agents once; they resumed and finished.

- **Built.** The masker as a domain operation in its own package `operations/masking` (one package per operation, like canonical JSON and event validation), the six detectors ported with their pattern texts unchanged, the default list of names, `MaskerOptions` (extra patterns, replace or add field names, classes and rules), and `MaskingService` that masks `data`, `attributes` and `context` of an envelope and returns an error and no envelope on any failure. See section 2.12 of the architecture document.
- **The shared tables.** `text`, `field_names` and `values` (116 cases, plus the 17 of the folding table) have the **old library as the oracle**: the coordinator ran the old Go masker over the inputs, so the new code in both languages is checked against the behavior that was in production, not against itself. The 16 envelope cases (new options, scope, untouched fields) were computed by hand with Node.js. All pass in Go and in Python with no edit of any fixture. One expected value changed on purpose (`class_redact`) made both languages fail; restored, both pass.
- **A differential test beyond the tables.** 6000 random strings made of the sensitive pieces and awkward characters went through the Go masker and the Python masker. It found 22 differences, all caused by the case folding of Go (the Kelvin sign and the long s fold to `k` and `s` in a case-insensitive pattern) that Python did not do, so **Python hid less than Go**. The Python translation of the patterns now does the same folding and the cases are in `text_unicode_folding.json` (17 cases, with the expected values taken from Go). The differential test was then re-run on **30000 random strings with a different seed: 0 differences**.
- **Verification.** Go: `gofmt` and `goimports` clean, vet and build clean, all tests pass (architecture tests included), coverage **99.2%**. Python: `ruff` clean, **227 tests**, coverage **100%**. The registry: `REQ-SEC-002` and `REQ-SEC-003` have tests; `REQ-SEC-001` waits for T-03.9 (19 of 130 covered, 103 pending, 8 without a task).
- **Choices, each with the maintainer not asked.** `body`, `content` and `payload` stay on the default list (the open question of the task). The patterns are shared text and Python translates them (ASCII word boundaries, the exact white space of RE2, flags, folding). A consumer's extra pattern must stay in the common subset. A class with no rule is redacted. `allow` skips only the name rule. A direct call of `MaskValue` on a field of a `drop` class returns the value masked, never raw (only the enclosing map removes the key). Names are normalized the same way for the list and the classes. An empty name is ignored, so it cannot hide everything. Resource and actor are not masked.
- **Known gaps.** The spying-sink proof builds the chain inside the test; the real wiring is T-03.9, where a test must prove that no path reaches a sink without the masking service. The detectors do not see a secret split across two fields. Python `date` and `timedelta` values are hidden as uninspectable. Case folding of exotic characters in field names (for example U+0130) is not equal in both languages. The limits (T-03.5) and the configuration mapping (T-03.6) come next.
