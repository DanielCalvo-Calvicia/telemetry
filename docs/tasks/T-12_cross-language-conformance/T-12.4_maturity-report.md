## Goal

Generate a report of the level of each capability (`stable` or `beta`) and of the library as a whole, which is the level of the least complete capability (REQ-CNF-008), so the decision of T-13.5 rests on a file and not on a guess.

## Design notes

- The input is `contracts/capabilities/registry.yaml` and the result of the gate of T-12.2. A capability is `stable` only when it is supported in both languages (REQ-CNF-007) and its definition of done holds (PR-001 section 17); otherwise it is `beta`.
- The library level is `stable` only when every capability is `stable`; one `beta` makes it a beta (`0.x`). Q09-6 answered that there is no `1.0` until every process works, so the report has no partial `1.0` rule.
- Capabilities that are deferred by decision (the OpenTelemetry and Prometheus adapters, the audit adapter) appear in the report as `deferred`, with their reason, and are not counted as incomplete capabilities. This is the proposed reading: the capability (metrics, audit) is complete without an adapter nobody needs yet. Open question to the maintainer: confirm that reading before T-13.5.
- The report is a generated Markdown file, committed under `docs/`, plus a non-zero exit code option for CI. It is derived data: nobody edits it by hand and CI checks that the committed copy equals a fresh run.
- No secrets or internal names: the report lists only capability identifiers, languages and levels.

## Acceptance criteria

- The report lists every capability with its level in Go and Python and the library level.
- One `beta` capability makes the library level `beta`; a deferred one is listed with its reason and does not.
- The committed report equals a fresh run, and CI fails when it does not.
- Ends with the checks of the README section 3 green in every language the task names.
