## Goal

Let `contracts/capabilities/registry.yaml` mark a capability as supported only when both languages pass its conformance tests, and treat an adapter of one language only as "not applicable" in the other without blocking the capability (REQ-CNF-007, REQ-AI-011).

## Design notes

- Extends the Go check of T-02.7 (which fails when a `REQ-*` has no conformance test). Each registry row names its conformance tests; the gate reads the result of the runner of T-12.1 and the language test results, and fails when a status says `supported` in Go or Python and the matching tests did not pass.
- The statuses of each language are a closed list in `contracts/enums/` (for example `planned`, `built`, `supported`, `not_applicable`); the exact values are fixed in T-02.7 and are not invented here. `not_applicable` is allowed only for an adapter that exists in one language (LangChain and LlamaIndex, Python only) and the row must say why.
- The gate is a tool the CI calls, not code that runs in the library. It lives in Go because the generator is Go (REQ-CNF-002).
- A status is never edited by the tool: the gate only checks, and a person changes the registry in the pull request that makes the tests pass.
- Open question to the maintainer: when a test is skipped in CI (for example the Raspberry Pi pilot of T-08.6 or the agent pilot of T-09.9, which need the maintainer), does the capability stay at `built`? This is the proposed reading.

## Acceptance criteria

- A row marked supported with a language whose tests fail makes the gate fail and names the capability and the language.
- A `not_applicable` row without a reason, or for a capability that exists in both languages, is rejected.
- A one-language adapter marked `not_applicable` in the other does not block its capability.
- Ends with the checks of the README section 3 green in every language the task names.
