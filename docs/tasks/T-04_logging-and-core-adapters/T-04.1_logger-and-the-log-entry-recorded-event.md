## Goal

Give the library its logger: one method per severity, each call building a `log.entry.recorded` event with the building blocks of T-03 and handing it to the log sinks.

## Design notes

- One method per severity of the contract (`TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `CRITICAL`, section 5.3); names follow `contracts/conventions/naming.md` (REQ-ARC-010).
- The event: category, function and message in `data`; the application in `resource.service_name`; extra fields in `attributes`, under the limits of T-03.5 (REQ-LOG-007, REQ-CTR-010). `trace_id`, `span_id` and `execution_id` come from the call context of T-03.8 into `context` (REQ-LOG-005). The function name keeps the call-depth rule of today's `call_depth` helper.
- Native logging (REQ-LOG-002): in Go an `slog.Handler` that turns a record into the same event; in Python a `logging.Handler`. Each maps the native level to the severity enum.
- Request bodies and arbitrary payloads are never recorded unless the caller passes them as fields (REQ-LOG-006); there is no automatic body capture.
- Masking happens inside the building of the event, before any sink (ADR-006, T-03.4). There is no code path that logs unmasked.
- The logger hands the event to the `LogSinkPort`. That call is the place where T-05.1 puts the queue; until then it is a development stage and the dispatch is not claimed to be non-blocking.
- Question to the maintainer: the old library returned an error only when the entry could not be built. REQ-CTR-002 says an invalid event is rejected "with a classified error, without throwing to the hot-path caller". Does a log call return that error, or only count it in diagnostics (T-05.5)?

## Acceptance criteria

- A call at each severity produces a `log.entry.recorded` event that validates against its schema.
- `data` has category, function and message; `resource.service_name` is the application; extra fields land in `attributes`; the limits of T-03.5 apply.
- With a trace and an execution in the context, the event carries them.
- A secret in a field or in the message is masked in the event.
- The `slog` handler and the `logging` handler produce the same fixture bytes as a direct call.
- No request body is recorded by default.

Ends with the checks of the README section 3 green in every language the task names.
