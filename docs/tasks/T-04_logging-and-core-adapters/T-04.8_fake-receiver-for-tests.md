## Goal

A test helper that plays the receiver: it accepts batches, answers with the status codes of the failure matrix and lets a test assert what arrived. The real receiver is a separate project (Q03-1, Q07-9), so every test of delivery uses this fake.

## Design notes

- It listens on a local address (`localhost`, a free port) and exposes its URL to the test. It validates the body as `{"schema_version", "events"}` (REQ-OUT-010), decodes gzip, and checks the authentication header the test expects.
- A scripted answer per request: 200, 408, 429 with and without `Retry-After`, 4xx, 5xx, an invalid body, a slow answer longer than the timeout, a closed connection. The script is a list the test fills, so a test can say "fail twice, then succeed".
- It records every batch with its headers, in order, so a test can assert events, order and count, and can wait for N events with a timeout.
- It lives under the tests tree and is never part of the shipped code. It is not a receiver design: it asserts the contract of T-04.4 and nothing more (the library is not a backend, section 1.3).
- Used by T-04.5, T-05.1 to T-05.6, T-06.5 and the pilots. Question to the maintainer: should a copy for Python also be usable by the cross tests as a separate small process, or is one fake per language enough?

## Acceptance criteria

- A test can script a sequence of answers and read back the batches, headers and counts.
- The fake rejects a body that is not `{"schema_version", "events"}` and says why.
- It never listens on anything other than the local address and holds no credential beyond the test token.
- The Go and Python fakes answer the same script the same way.

Ends with the checks of the README section 3 green in every language the task names.

## Verification

The tests of the fake itself: each scripted status, gzip, a wrong token, a slow answer, a closed connection, and the wait for N events with a timeout.

## Notes

**Done 2026-11-03** (Go 1.25.5, Python 3.11.1). The coordinator wrote the 14 shared cases first; two agents wrote the fakes in parallel; the coordinator verified independently, ran a differential test and wrote the documents. The work was paused by a usage limit of the user and resumed from the state of the repository.

- **Built.** A fake receiver in each language (the API: `New`/`Receiver`, `URL`, `Script`, `Reset`, `Requests`, `Events`, `WaitForEvents`, `Close`; the types `Config`, `Answer` and `Request`), the shared script cases, and the use of the fake in the two-destinations test of the HTTP destination in both languages. See section 2.23 of the architecture document.
- **Verification.** The 14 shared cases pass in both languages with no edit. One expected status changed on purpose made both fail, restored both pass. A **differential test of 500 random scenarios** found one difference (Python checked the size of a body before the authentication, Go after: an oversized body from an unauthenticated client was 413 in Python and 401 in Go); Python was aligned (authentication first) and the second run gave **0 differences** in the statuses and in every field of the records. Go: `gofmt` and `goimports` clean, vet and build clean, all tests pass, coverage **98.1%** (the fake itself 98.8%; the lines not covered are a panic in `New` and a hijack error that cannot be reached with a real server); `go.mod` still has no `require` line. Python: `ruff` clean, **665 tests**, coverage **100%**.
- **Open question, decided with the default.** One fake per language is enough; a separate process for the cross tests (T-12) is not built. The maintainer was not asked.
- **Choices.** The folder is `tests/fakes/fake_receiver` (deviation from the task). The check order is: gunzip and size, authentication (401, the script is not used), 413, gzip (400), validation (400). A rejected request is recorded with its reason; the script is used only by valid, authenticated requests. A client that disconnects before the body is complete is not recorded and not answered in Python (Go's behavior for that case is not in the shared cases). The Go-side fake drains up to 64 MiB more of an oversized body so the client can read the 413.
- **Known gaps.** The 8 MiB tests make the Python tests of the fake take about 30 s. Duplicate keys in a JSON body are not detected. The fake is not used yet by the other tests of the HTTP client and destination (they keep their ad hoc servers except one test each).
