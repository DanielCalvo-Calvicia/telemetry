## Goal

In Go and in Python: `command_id` and `deadline` on command events, so the request, the result of the driver and the observed state are three separate events that can be joined (REQ-DEV-006, REQ-DEV-010).

## Design notes

- The three events (B.4 and B.5 of Annex B): `device.command.requested` (what was asked, with `deadline` when the consumer has one), `device.command.completed` (the result according to the consumer's driver code, `execution_status`) and the observed state (`device.state.observed` or `device.actuator.changed` with `cause_command_id`).
- A successful command does not prove that the physical state was reached (REQ-DEV-006): `observed_state` of the completed event is the value the consumer reports, and the library never copies it from, or into, the state event.
- The library only records. The consumer's code executes the command and honors the deadline (REQ-DEV-010); the library does not enforce a deadline, does not time a command out and keeps no table of pending commands. Telemetry is not a safety mechanism (REQ-DEV-001).
- A command and an actuator change are different events from a reading (REQ-DEV-008).
- `command_id` must be unique. Question to the maintainer: does the library generate it (UUIDv7 through `IDGeneratorPort`) when the consumer gives none, or must the consumer always give it?
- `deadline` and `requested_at` use the fixed UTC time format of REQ-CNF-003, like every instant of the contract.

## Acceptance criteria

- A request, a result and an observed change for one command carry the same `command_id` and are three events with three different `event_id` values.
- A request with a deadline carries it; one without a deadline carries none.
- A completed event with `succeeded` and an observed state that differs from the requested one is accepted and sent as given.
- A command with a missing `command_id` is rejected, or gets a generated one, as the answer to the question above says.
- The library starts no timer and keeps no pending-command state.
