## Goal

Write the seven `device.*` schemas and the device enums in `contracts/`, so the generator (T-02.4) gives both languages the same types (REQ-DEV-002, REQ-DEV-004, REQ-DEV-005). The task is a contract and has no language of its own; the generated Go and Python code is checked by both.

## Design notes

- The seven event types of section 8.2: `device.measurement.recorded`, `device.state.observed`, `device.actuator.changed`, `device.command.requested`, `device.command.completed`, `device.connectivity.changed`, `device.health.reported`. The fields of `data` are those of the table of 8.2.
- The schemas are generic: none names a sensor model, an actuator type or a manufacturer (REQ-DEV-004). Specialization is `kind`, `name` and `attributes`.
- `value` of a measurement is a number, a boolean or text (a `oneOf`). `quality` takes `good`, `uncertain`, `bad`, `stale`; `execution_status` takes `succeeded`, `failed`, `timed_out`, `cancelled`, `rejected`; `kind` starts with `temperature`, `voltage`, `gnss`, `imu`, `rpm` (REQ-DEV-005). Adding a value is a MINOR change (REQ-VER-003).
- The device is the `actor` with `kind=device` (section 5.2); the value `device` must exist in the actor kind enum of T-02.2.
- That `occurred_at` equals `observed_at` (REQ-CTR-008) cannot be written in a JSON schema: T-03.3 enforces it and T-08.5 tests it.
- Questions to the maintainer:
  1. Annex B proposes `digital_input` and `position` as values of `kind`. Confirm or drop each (the examples use only `digital_input`; no example uses `position`).
  2. The values of `status` (connectivity, subsystem health) are not listed in the specification. Which ones?
- `device.health.reported` lists subsystems with `component`, `status`, `detail`; it is independent of the health model of T-07.4.

## Files

- `contracts/schemas/device/` (seven files, one per event type, in `snake_case` like the JSON fields)
- `contracts/enums/device/kind.yaml`, `quality.yaml`, `execution_status.yaml`, `status.yaml`
- `contracts/capabilities/registry.yaml` (the device entry), `contracts/enums/` (the `device` actor kind, if missing)
- Generated code: committed output of the generator in `go/internal/domain/` and `python/src/telemetry/internal/domain/` (never edited by hand)
- Tests: `go/internal/tests/contract/device_schemas_test.go`, `python/internal/tests/contract/test_device_schemas.py`; fixtures in `integration-tests/fixtures/device/` (valid and invalid samples)

## Acceptance criteria

- Each schema accepts its valid sample and rejects one with a missing required field, a wrong type and a value outside its enum.
- A reading of a sensor kind invented for the test (not in any schema) validates with a new `kind` value and no schema change.
- The generator produces the enums and types for both languages and CI sees no difference.
- The questions above are answered and the answers are written here as a Resolution or as a dated note in the contract documents.

Ends with the checks of the README section 3 green in every language the task names.
