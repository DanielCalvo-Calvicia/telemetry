## Goal

In Go and in Python: configurable sampling and batch sending for high-frequency readings, sent to an events or SQLite destination and never to metrics (REQ-DEV-009, REQ-MET-004).

## Design notes

- Reference case (Q04-4): a microcontroller sensor that samples every 50 ms, that is 20 readings per second, each one an event like B.1 of Annex B (B.8).
- Readings go only to destinations that accept events (HTTP, file, SQLite, the spool). `MetricsSinkPort` never receives a device reading: a test proves it.
- Batching uses the bounded queue and the batch of T-05.1 (default batch 100, flush every 2 s); sampling decides which readings enter the queue.
- Everything is configurable (REQ-DEV-009), so the new settings are `Config` fields with tags: the same names in both languages and in `docs/configuration/environment-variables.md`.
- Time stays honest: a sampled reading keeps its own `occurred_at` and `observed_at`; the library does not move them to the batch time.
- Questions to the maintainer:
  1. Which sampling policies are needed: keep one reading every N, a minimum interval, only on change (with a tolerance), or a subset of these?
  2. Is the batch only the delivery batch of the destination (no new event), or does a batch of readings travel as one event? The specification says "batch sending" without a new event type.
  3. Are readings dropped by sampling counted in the diagnostics of T-05.5, like the other drops?

## Acceptance criteria

- With a fake clock and a 50 ms source over one minute, each configured policy sends the expected number of readings and the expected batches.
- No reading reaches the metrics port, with any configuration.
- Turning sampling off sends every reading and loses none while the queue is not full.
- Each reading keeps its original `occurred_at`.
- An invalid sampling configuration is rejected at start with an error that names the field.

Ends with the checks of the README section 3 green in every language the task names.
