## Goal

The third delivery mode: events go to the spool before they are sent and stay there until the destination confirms them, so delivery is at-least-once while the spool is not full or corrupted (10.1, REQ-SPL-001 to REQ-SPL-003).

## Design notes

- The log call still only enqueues (REQ-DLV-002); the worker writes the batch to the spool, sends from the spool in order, and deletes records on confirmation (REQ-DLV-003). The mode is chosen per destination (T-05.3); the profiles `robotics` and `offline_device` default to it (REQ-CFG-004).
- Recovery: at start the worker first sends what the spool already holds, in order.
- Full spool, the table of 10.3: a `critical` event replaces the oldest of lower classes, or if there are none the oldest `critical`, and the drop is counted; a `normal` or `bulk` event is rejected and counted.
- Corrupted records are isolated and counted, and the rest continues (REQ-SPL-002). If the storage is unavailable at start the destination degrades to `retry`, says so in diagnostics (T-05.5) and continues (REQ-SPL-003).
- Duplicates can arrive: a timeout after the server processed a batch makes a resend. The library does not claim exactly-once; `event_id` is for the receiver (REQ-DLV-001, Q03-7).
- A public cleanup function for the project (REQ-SPL-001, Q07-11). Questions to the maintainer: what it removes (everything, or older than a given time or a given count) and its name; the proposal is a time or count argument plus a way to remove all.
- How the consumer gives the spool to the core: the spool adapter is passed in code like every optional adapter (REQ-ARC-013) and the directory is a setting. Asking for `durable` with no spool passed is a configuration error at start (REQ-CFG-002). The SQLite destination never uses the spool (REQ-OUT-009).
- `flush` and `shutdown` (T-05.4) now fill the "left in the spool" count.

## Acceptance criteria

- With the network down, events are kept in the spool and none is sent; when it is back they are sent in order and then deleted.
- After a restart with unsent events, the new process sends them first.
- Each case of the full-spool table gives the documented result and counter, in both languages.
- A damaged record is isolated and counted; delivery continues.
- With an unusable spool directory the destination runs as `retry` and diagnostics say so.
- The cleanup function empties what the project asks it to empty and nothing else.

Ends with the checks of the README section 3 green in every language the task names.
