## Goal

A destination that writes events to a local SQLite file a reader can query, like the AWS HTTP sink but to a file (REQ-OUT-009, Q07-12, Q08-5, Q09-5).

## Design notes

- It is written like any destination: several can be active at once, events are masked before it (ADR-006) and limited, and its failure never stops the others (REQ-DLV-005, ADR-005). It takes batches from the queue of T-05.1 in the modes of T-05.3. It has no spool in front of it, because a write to a local file is already durable; asking for `durable` on it is a configuration error.
- It writes the layout of T-06.1: one `events` table with the envelope as JSON and the indexed columns; a batch is one transaction; the file opens in WAL mode and a new file gets its `user_version`. An existing file with an unknown version is refused at start (REQ-CFG-002).
- Retention is done only by the writer, and rows stay until the project cleans them. A public function to delete rows by age or by count is part of this task; its name and arguments are decided with the maintainer, in the same way as the spool cleanup of T-06.5.
- A locked database or a full disk is a transient failure; a write error is classified and returned as a value (ADR-005). The reader never writes (Q09-5), so there is only one writer and no lock rules beyond a busy timeout.
- Public package names are open. PR-001 calls the adapter "SQL (SQLite first)" and the rule is `<functionality>/<adapter>`: the proposal is `go/pkg/sql/sqlite` and `telemetry.sql.sqlite`, with the extra `telemetry[sqlite]` in Python. Question to the maintainer, who may name another functionality.
- Second question to the maintainer: the two SQLite modules (this one and the spool of T-06.3) need the same code to open a database (driver, WAL, version check). Duplicate that small piece in each module, or share it in a third module?
- The Go module uses the driver chosen in T-06.2; this task does not list T-06.2 as a dependency in the source plan, but it needs it before its Go side can start.

## Acceptance criteria

- A batch of events becomes rows whose indexed columns equal the envelope fields and whose JSON equals the canonical envelope, in both languages.
- A reader that opens the file read-only sees the rows while the writer keeps writing.
- A file with an unknown layout version is refused with a classified error.
- A failing write is dropped or retried by the mode and never stops another destination.
- The retention function deletes only what it is asked to.

Ends with the checks of the README section 3 green in every language the task names.
