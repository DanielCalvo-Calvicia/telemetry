## Goal

In Go and in Python: the health model of an application, with liveness, readiness, health per dependency and per subsystem, degraded status, last good operation and last heartbeat, offered as interfaces the consumer exposes (REQ-HLT-001 to REQ-HLT-003).

## Design notes

- No HTTP server (REQ-HLT-002): the library returns a snapshot value that the consumer exposes through its own adapter, if it wants to.
- A failure of the telemetry exporter never marks the application unhealthy by itself (REQ-HLT-003). The diagnostics of T-05.5 describe the exporter; health describes the application. The two are kept apart, and a test proves it.
- The heartbeat is the last instant at which the consumer said "I am alive"; the library stores it and may report it as an event.
- Health events need a registered schema (REQ-CTR-002). The specification names "the health events" (Q02, question 5) without listing them, so the event types are open.
- Questions to the maintainer:
  1. Event type names and fields of the health events (state change only, periodic report, or both).
  2. The values of a health status (for example `ok` and `degraded`; `down` and `unknown` are not in the specification).
  3. How does a dependency report: the consumer registers a check callback that the library calls, or the consumer pushes a status?
  4. Is the heartbeat emitted by a timer of the library (and with which interval), or only when the consumer calls it?
- `device.health.reported` belongs to T-08 and has its own schema; this task does not reuse it.

## Acceptance criteria

- The snapshot shows liveness, readiness, one status per dependency and per subsystem, degraded, last good operation and last heartbeat.
- With every destination failing, the readiness of the application does not change by itself.
- The library starts no listener and imports no HTTP server.
- A degraded dependency makes the application degraded and not down, as documented.

Ends with the checks of the README section 3 green in every language the task names.
