## Goal

In Go and in Python: the `execution.*` events and the public API that lets a cronjob, a worker, a task, an AI run or a mission report its life cycle in one shape (REQ-EXE-001, REQ-EXE-004, REQ-EXE-005).

## Design notes

- An execution event carries `execution_id` (in `context`, REQ-CTR-001), `parent_execution_id`, attempt number, progress, error classification and cancellation reason (REQ-EXE-005). Logs written inside an execution attach its id from the call context (REQ-LOG-005).
- The state of the execution is separate from the delivery state of the report (REQ-EXE-004): the event says `completed`; whether it reached a destination is shown only by the diagnostics of T-05.5. No event field mixes the two.
- The error classification reuses the failure model of T-07.3 and the catalog of T-02.3.
- `execution_id` is never a metric attribute (REQ-CTR-006).
- Every transition goes through the domain of T-07.1; an invalid one is rejected at the source with a classified error and never throws to the caller (REQ-CTR-002).
- Questions to the maintainer (the specification names the family `execution.*` only):
  1. One event type per state change (for example one per state) or a single event type that carries the new state in `data`?
  2. How is progress expressed: a fraction from 0 to 1, or done and total?
  3. Is the cancellation reason free text or a value of an enum in `contracts/enums/`?
- The public names follow `contracts/conventions/naming.md`; the final list is written in `docs/api/api.md`.

## Acceptance criteria

- A full life cycle (start, progress, retry, completion, failure, cancellation, timeout) produces events that validate against their schemas in both languages.
- A child execution carries the `parent_execution_id` of its parent.
- An invalid transition is rejected and no event is sent; the caller does not receive a panic or an exception.
- No event carries delivery information.

Ends with the checks of the README section 3 green in every language the task names.
