## Goal

In Go and in Python: `fault.*` events with the failure classification, and `report.*` events with a typed payload for operational events that fit no other capability (REQ-FLT-001, REQ-RPT-001).

## Design notes

- A fault carries code, category, severity and recoverable or not (REQ-FLT-001). The categories live in `contracts/enums/`. T-02.3 already writes the first failure classification; this task adds the `fault.*` events and the public API on top of it and does not duplicate the enum.
- A report is for operational events that do not fit another capability (REQ-RPT-001). Each event type needs a registered schema for `data` (REQ-CTR-002).
- The message and the details of a fault pass through the masking of ADR-006 like any event; by default no stack trace or payload is recorded (REQ-LOG-006).
- A fault can be related to an execution: it takes the id from the call context, it does not own it.
- Questions to the maintainer:
  1. Event type names: only the families `fault.*` and `report.*` are fixed. Which types are in the first version?
  2. Is the `severity` of a fault the envelope enum (`TRACE` to `CRITICAL`, section 5.3) or a separate scale?
  3. "Typed payload": does each kind of report register its own schema and event type, or is there one `report` event with a `report_type` whose payload is validated against a registered sub-schema?
- A fault event and an execution `failed` event are different facts; the API does not emit one from the other unless the consumer calls both.

## Acceptance criteria

- A fault with each category and each recoverable value validates and serializes in both languages.
- A report whose payload does not match its schema is rejected at the source with a classified error.
- A fault message that contains a token reaches the sink masked.
- The same sample fault gives the same canonical JSON in Go and in Python.

Ends with the checks of the README section 3 green in every language the task names.
