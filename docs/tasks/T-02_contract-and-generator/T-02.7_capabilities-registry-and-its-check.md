## Goal

Write the format of `contracts/capabilities/registry.yaml` and a check that fails when a requirement has no conformance test.

## Design notes

- Section 2 of the specification: every `REQ-*` is linked, in the registry, to at least one conformance test. Section 6 and REQ-CNF-007: each capability lists its identifier, public API, schemas, configuration, error semantics, ports and adapters, the state in Go and in Python, and the conformance tests. A capability is marked supported only when both languages pass (REQ-CNF-007).
- Maturity level per capability: `stable` or `beta` (section 13.3). The overall maturity is that of the least complete one (REQ-CNF-008, Q09-6). A language state is `todo`, `built`, `passing` or `not_applicable` (for the Python-only frameworks, REQ-AI-011, Q07-14).
- The capabilities of the plan are the ones of the build order of Q07-16: core and delivery, logs, executions and faults, health, reports, devices, AI, metrics, traces, audit. This task writes the format and the entries of the first capabilities (envelope, logging); the others are added by their epics with `state: todo` so the check shows what is missing.
- The check is a Go program that reads the registry and the requirements document and fails on a `REQ-*` identifier that no capability lists or that lists a test that does not exist. The YAML dependency question is the same as for the generator (T-02.4): use the module chosen there. The requirement list comes from `docs/requirements/requirements.md`; open question: is that table the source of the identifiers, or is a list kept in `contracts/`? Default if unanswered: the requirements document.
- A requirement may be marked `pending` with the task that will write its test, so the check can run from day one without hiding the gap. A `pending` item never counts as covered.

## Files

- `contracts/capabilities/registry.yaml` (format and first entries)
- `contracts/capabilities/README.md` (the fields and the states)

- `.github/workflows/ci.yml` (a step that runs the check)

## Acceptance criteria

- The check passes on the registry of this task and fails on a fixture where a `REQ-*` has no conformance test.
- It fails when a listed test file does not exist, and when a capability is `passing` in one language and `todo` in the other while marked supported.
- `not_applicable` is accepted only with a written reason.
- The output lists the uncovered requirements, one per line, with their area.
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

Tests of the check on the three fixture registries; a run on the real registry and requirements document.
