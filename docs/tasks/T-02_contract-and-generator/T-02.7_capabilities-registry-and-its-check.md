## Goal

Write the format of `contracts/capabilities/registry.yaml` and a check that fails when a requirement has no conformance test.

## Design notes

- Section 2 of the specification: every `REQ-*` is linked, in the registry, to at least one conformance test. Section 6 and REQ-CNF-007: each capability lists its identifier, public API, schemas, configuration, error semantics, ports and adapters, the state in Go and in Python, and the conformance tests. A capability is marked supported only when both languages pass (REQ-CNF-007).
- Maturity level per capability: `stable` or `beta` (section 13.3). The overall maturity is that of the least complete one (REQ-CNF-008, Q09-6). A language state is `todo`, `built`, `passing` or `not_applicable` (for the Python-only frameworks, REQ-AI-011, Q07-14).
- The capabilities of the plan are the ones of the build order of Q07-16: core and delivery, logs, executions and faults, health, reports, devices, AI, metrics, traces, audit. This task writes the format and the entries of the first capabilities (envelope, logging); the others are added by their epics with `state: todo` so the check shows what is missing.
- The check is a Go program that reads the registry and the requirements document and fails on a `REQ-*` identifier that no capability lists or that lists a test that does not exist. The check is its own Go module, `tools/registry_check`, with the same layers as the generator and the same YAML library. **The source of the requirement ids is the specification (PR-001), not the requirements document**: the document lists only the requirements whose state moved (a handful), so it cannot be the source of "every `REQ-*`"; the check takes the path of the source in a flag (`--spec`), so it can change. This was decided by the coordinator because the plan's default does not work, and the maintainer was not asked.
- A requirement may be marked `pending` with the task that will write its test, so the check can run from day one without hiding the gap. A `pending` item never counts as covered.

## Acceptance criteria

- The check passes on the registry of this task and fails on a fixture where a `REQ-*` has no conformance test.
- It fails when a listed test file does not exist, and when a capability is `passing` in one language and `todo` in the other while marked supported.
- `not_applicable` is accepted only with a written reason.
- The output lists the uncovered requirements, one per line, with their area.
- Ends with the checks of the README section 3 green in every language the task names.

## Notes

**Done 2026-10-29** (Go 1.25.5). The code was written by a delegated agent from a precise brief and then **verified independently** by the coordinator (the numbers below are the coordinator's).

- **What was built.** `tools/registry_check/` (`main.go`, `README.md`, `internal/domain` with the model, the 19 sentinels, the rules and the report; `internal/application` with the ports and the use case; `internal/infrastructure` with the command line and the readers of the registry, the specification, the test files and the tasks, whose I/O is in `external/` folders; `internal/composition_root`); `contracts/capabilities/registry.yaml` (format and 17 capabilities) and `contracts/capabilities/README.md` (every field and state); the job `registry-check` in `.github/workflows/ci.yml`; `./tools/registry_check` in `go.work`. Flags: `--spec`, `--registry`, `--root`, `--tasks`. Exit codes: 0 pass, 1 fail, 2 usage.
- **The format.** A capability has `id`, `title`, `level` (`stable`/`beta`), `status` (`supported`/`in_progress`/`planned`), `description`, `public_api`, `schemas`, `configuration`, `errors`, `ports`, `adapters`, `languages` (`go` and `python`, each `todo`/`built`/`passing`/`not_applicable` with a reason) and `requirements`. A requirement is `id` plus either `tests` (language and an existing path) or `pending` (a task id, or `unassigned`). A requirement belongs to one capability only; `supported` needs both languages `passing` (or `not_applicable` with a reason for one) and every requirement covered by tests.
- **Verification (coordinator).** The specification has **130** requirement ids (counted separately with `grep`). `gofmt` and `goimports` print nothing and `go vet`, `go build` and the tests pass for `tools/registry_check`, `tools/contract_generator` and `go/`; coverage is **98.7%**, **98.7%** and **99.0%**. The real check exits 0: `requirements: 130 total, 10 covered by tests, 112 pending, 8 no task yet, 0 not accounted for` and `library maturity: beta (least complete capability: configuration, planned)`. **Negative proof:** pointing one test path at a file that does not exist makes the check exit 1 with `...: test file does not exist`; restoring the registry gives exit 0. The agent's tests cover each failing fixture and its reason (18 fixture registries): an uncovered requirement, a missing test file, `supported` with a language `todo`, `not_applicable` without a reason, an unknown requirement, an unlisted requirement, a missing pending task, invalid values, duplicates, broken YAML, a missing registry, spec or tasks folder.
- **A correction made by the coordinator.** The agent linked four requirements to tests on partial evidence. Three were moved back to `pending` because the tests do not prove the whole requirement: `REQ-CTR-001` (the versioned envelope and the UUIDv7 id wait for T-03.1), `REQ-CTR-010` (the configurable limits and the truncation wait for T-03.5) and `REQ-CNF-002` (the configuration schema is generated from T-03.6). `REQ-CNF-001` stays covered (the generator byte comparison plus the CI drift check). This is why 10 and not 13 requirements are covered.
- **Real gaps found in the task plan: 8 requirements that no task mentions** (`pending: unassigned`): `REQ-ARC-004` (abstractions model capabilities, not third-party methods), `REQ-CFG-003` (the precedence of defaults, profile and options), `REQ-DEV-003` (device events combined with execution, fault and report events), `REQ-DEV-007` (the fields of a measurement), `REQ-LOG-004` (several independent destinations at once), `REQ-MET-002` (a metric has name, description and unit), `REQ-OUT-007` (a new adapter touches only its port), `REQ-VER-002` (each package declares the contract versions it supports). Each needs a task (or a line in an existing one) and then its registry entry points at it.
- **Pending on tasks that are already done.** `REQ-DST-003` points to T-01.3 and `REQ-VER-004` to T-02.2, the only tasks that mention them; both tasks are done and no test proves either requirement, so the check cannot tell they are stale. They are real gaps too.
- **Weak assignments.** Where several tasks mention a requirement the agent picked the not-yet-done leaf that implements it; some picks are weak, for example `REQ-ARC-012` to T-08.2, `REQ-DST-004` and `REQ-AI-009` to T-09.2, `REQ-CTR-005` to T-03.1, `REQ-CNF-001` and `REQ-VER-003`. Revisit them when those tasks start.

Decide, when their capabilities start, whether such a requirement is covered by a review checklist or a check in CI.
- **Not enforced, on purpose.** A `supported` capability does not require tests in each applicable language for every requirement.
