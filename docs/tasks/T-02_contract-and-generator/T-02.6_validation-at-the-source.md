## Goal

Reject an event whose `data` does not match the schema of its `event_type`, with a classified error and without ever throwing to the caller.

## Design notes

- REQ-CTR-002: each event type has a schema; an event that does not validate is rejected at the source with a classified error. REQ-DLV-002 and ADR-005: the hot-path call (log, metric, event) never throws and never blocks. The rejection is returned as a value or counted in diagnostics; the caller of `Log(...)` gets no panic and no exception.
- REQ-CTR-003: the types are validated against the schema. The question was whether the core uses a JSON Schema library (a) or the generator emits plain validation code (b). The maintainer was not asked; the task's default, **(b)**, was used because the core must keep a minimal set of dependencies (REQ-ARC-005). The schemas stay the single source (REQ-CNF-001) and the registry is read at generation. Changing to (a) would replace the generated validators by a library call.
- The rejection uses the error codes of T-02.3 (an event that fails its schema, an unknown event type). The error names the event type and the field path, never the value (a value may be a secret; masking is T-03.4).
- Validation runs once per event, after masking is decided and before the event reaches a queue. Where it is called from (the building service) is T-03.3; here the validator is a pure function in the domain layer and a thin wrapper that returns the error.
- A schema change that makes old events invalid is a MAJOR change of the contract (REQ-VER-003).

## Acceptance criteria

- A valid `log.entry.recorded` event passes; one with a missing required field, a wrong type or an unknown event type is rejected with the right error code.
- No call path panics or raises to the caller on any invalid input, including `nil`/`None` and a payload that is not an object.
- The error message contains the event type and the field path and does not contain the offending value.
- Go and Python give the same error code for the same invalid fixture.
- Ends with the checks of the README section 3 green in every language the task names.

## Notes

**Done 2026-10-29** (Go 1.25.5, Python 3.11.1). The code was written by a delegated agent from a precise brief (it was interrupted once by a session limit and resumed) and then **verified independently** by the coordinator (the numbers below are the coordinator's).

- **What was built.** The generator emits a validator per registered event type in both languages (new flags `--go-validation-out`, `--python-validation-out`; the full command is in the architecture document and the generator README; the use case renders every target before writing any, so nothing is written if one fails). The hand-written core: `ValidateEvent` / `validate_event`, the rules (`ValidateObject`, `ObjectRules`, `FieldRule`, `CheckString`, `CheckNumber`, `CheckInteger`, `CheckBoolean`, `CheckEnum`, `CheckObject`, `CheckAttributes`; the same in snake_case in Python), `Safely` / `run_safely`, and the errors `ErrEventSchemaInvalid` and `ErrEventTypeUnknown` (Go) and `EventSchemaInvalidError`, `EventTypeUnknownError` (Python). The architecture document, section 2.6, describes the behavior.
- **The open question, default used.** Option (b), no library in the core. It is easy to revisit: only the generated validators and the generator renderer would change.
- **Shared fixtures.** `go/internal/tests/fixtures/event_validation/valid_cases.json`, `invalid_cases.json` (24 invalid cases, each with the expected code, path and message) and `constructs/valid.json`, `constructs/invalid.json` (10 valid and 29 invalid cases of the other constructs: enum, nested object, attributes, integer, boolean, lengths). The Python tests read the same files. Go and Python assert the same code **and the same exact message** for the same case. A fake secret-looking value (`FAKE-SECRET-VALUE-1234`) is checked never to appear in a message.
- **Verification (coordinator).** Generator module: `gofmt` and `goimports` print nothing, `go vet`, `go build` and 8 test packages pass, coverage **98.7%** (was 98.1%). `go/`: gofmt and goimports clean, vet and build clean, 4 test packages pass including the architecture tests, coverage **99.0%**. Python: `ruff check` and `ruff format --check` pass (45 files), **68 tests** pass, coverage **100%** (367 statements). The real generator ran twice and **all 10 generated files are byte-identical**. **Drift proof:** adding `function` to `required` in `entry_recorded.schema.json` changed the generated output (hash `b8bd...` to `16cc...`); restoring the schema and regenerating gave the original hash back and `git status contracts` was clean. The canonical JSON comparison still gives `2 of 2 cases are identical in Go and Python`. The workflow YAML parses, keeps `contents: read` and pinned actions.
- **Panic and exception safety, two layers.** The code has no failure path by design, and `Safely` / `run_safely` turn anything unexpected into `event_schema_invalid` ("validation failed"); about 35 hostile inputs are tested plus a forced panic and a forced exception. `run_safely` does not catch `KeyboardInterrupt`.
- **A hole to settle before the first event type that uses context, resource or failure.** `pattern` is **not** validated (the generator refuses it for any schema an event reaches), and the common schemas `context` (`trace_id`, `span_id`), `resource` (`time_zone`) and `failure` (`code`) use `pattern`. An event type whose data references one of them will make the generator fail until `pattern` is supported (the Go and Python regular expressions differ slightly, so it needs care) or the schema changes. The envelope itself is not validated here for the same reason (`schema_version`, `event_id`, `event_type` and the times use `pattern`). Validating the envelope belongs to later tasks (T-03.3).
- **Smaller points.** The Go error text has the sentinel first and the detail on a second line (`errors.Join`); Python's `str(error)` is only the detail; the tests compare the detail and the codes are identical. An attributes limit written `4.0` is read as 4. The generated Python passes the attribute limits positionally to stay under 120 columns (it is excluded from ruff). A cyclic reference between two schemas is handled by the generator but not tested with a real schema. Python 3.10 is not installed here (the same 68 tests pass on 3.14).
- **Left for later.** `ValidateEvent` is called from the building of an event in T-03.3; the rejection counter is T-03.5 and T-05.5; the fixtures move to `integration-tests/fixtures/` in T-02.8.
