## Goal

Create the registry of event types and the catalog of error codes, with the first entries, so the generator and the error model have a source.

## Design notes

- Event types are `domain.entity.action` (REQ-CTR-001), each with a JSON schema of its `data` under `contracts/schemas/` (REQ-CTR-002). Each event type is added together with its capability (Q02-5: one at a time); this task creates the registry and the first type, `log.entry.recorded` (REQ-LOG-007, Q02-4): `data` holds the category, the function and the message, and the application goes to `resource.service_name`.
- The schema of `log.entry.recorded` keeps what the old `Entry` has (category, function, message; call context in `context`) and adds nothing that the old library did not carry. Its severity comes from the envelope.
- Error codes (REQ-CNF-004): one catalog shared by both languages, with a stable code, a category and a default message. Message text may vary per language; codes may not. This task writes the validation and configuration codes (an event that fails its schema, an unknown event type, a limit exceeded, an invalid configuration field, an unknown delivery mode).
- The failure classification of REQ-FLT-001 (code, category, severity, recoverable or not) is defined in the contract here as a schema and an enum only; its use (`fault.*` events) belongs to T-07.3. Decided by the maintainer on 2026-10-28: each capability adds its own error codes as it is built (the delivery codes are not written now).
- Where the registry and the catalog live was decided in T-02.1 (2026-10-28) (proposal: `contracts/events/registry.yaml`, `contracts/errors/catalog.yaml`).
- The old sentinels (`application/errors.go`, `domain/errors.go`) are not read: the new ones are written in T-03.7 from this catalog.

## Acceptance criteria

- Every registered event type points to an existing schema, and every schema file is registered (a check run by the generator in T-02.4).
- Every error code is unique, written in `snake_case` or the pattern the catalog documents, and has a category.
- A sample `log.entry.recorded` event with category, function and message validates; one without a message is rejected.
- The failure classification has the four fields of REQ-FLT-001.
- The open questions above are answered or listed as open in the folder README.

## Notes

**Done 2026-10-28.** Data and documentation only; the checks ran with `jsonschema` and `pyyaml` in a throwaway virtual environment (nothing was added to the repository).

- **What was built.** `contracts/schemas/log/entry_recorded.schema.json` (the `data` of `log.entry.recorded`); `contracts/events/registry.yaml` (one entry); `contracts/errors/catalog.yaml` (5 codes: `event_schema_invalid`, `event_type_unknown`, `limit_exceeded` (validation); `config_field_invalid`, `delivery_mode_unknown` (configuration)); `contracts/enums/failure_category.json` and `contracts/schemas/common/failure.schema.json`; the READMEs of `events/`, `errors/`, `schemas/` and `enums/`.
- **`log.entry.recorded` keeps what the old `Entry` has**, read from the old code: `message` is always present and any text, even empty, is valid; `category` is always serialized; `function` is optional (`omitempty`). So `data` requires `category` and `message`, allows `function`, and is closed. The application is the envelope `resource.service_name`, the call context is the envelope `context`, the severity is the envelope severity, and any extra field goes to the envelope `attributes` (REQ-LOG-007).
- **Where the schema lives.** The rule is `schemas/<domain>/<entity>_<action>.schema.json` for the type `<domain>.<entity>.<action>`; the earlier README of `schemas/` said "named like the type" and was corrected.
- **Failure classification.** Four fields (`code`, `category`, `severity`, `recoverable`) as REQ-FLT-001 asks. The categories are the two the first codes need (`validation`, `configuration`); each capability adds its own, which is a MINOR change. **For T-09.1:** the planned `ai.model.failed` schema uses `retryable` where this one uses `recoverable`; it has to be settled there.
- **The open question was answered by the maintainer on 2026-10-28.** The catalog does not hold the delivery codes now: each capability adds its own as it is built, as for event types. This is recorded in `contracts/errors/README.md`.
- **A bug the check found.** An unquoted colon in the description of `registry.yaml` made it invalid YAML; it is quoted now. This is why the registry is parsed and checked, not only read.
- **Verification.** The 10 schema and enum files are valid 2020-12 documents; the registry points every type to the schema its rule gives and every event schema is registered; the 5 codes are unique, lowercase `snake_case`, with a known category, a default message and a meaning; `log.entry.recorded` validates with category, function and message, without a function, and with an empty message; it is rejected without a message, without a category, with a numeric message, with an unknown field in `data`, and for an unregistered type; the failure schema accepts the four fields and rejects a missing `recoverable`, an uppercase code, a category that does not exist yet, a lowercase severity and a text `recoverable`. The envelope checks of T-02.2 (28 invalid samples) still pass.
- **Left for later.** The check as code over the registry and catalog is T-02.4; the fixtures are T-02.8; the old sentinels were not read (T-03.7 writes the new ones from this catalog).
