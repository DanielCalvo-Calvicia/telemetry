## Goal

Tell the project that uses the old library what happens to it: the old module path and its tags `v0.1.0` and `v0.2.0` stay available, and the new module is a different path, so nothing breaks until the consumer moves.

## Design notes

- The facts to state (PR-001, "How it relates to what exists today"): the old module is `github.com/DanielCalvo-Calvicia/telemetry` with the single public package `pkg/logging`; the new module is `github.com/DanielCalvo-Calvicia/telemetry/go` and adapters live under `go/pkg/<functionality>/<adapter>`; the two paths never clash.
- There is no deprecation period (Q01-3, Q08-2): the old surface disappears from the repository when T-04.7 removes it, but the tags stay in the module proxy and keep working for anyone who pinned them.
- A short mapping from the old API to the new one: the entry with fixed fields (`Application`, `Category`, `Function`, `Message`) becomes the `log.entry.recorded` event (category, function and message in `data`, the application in `resource.service_name`); the ready-made sink constructors of ADR-009 become adapters chosen in code (REQ-ARC-013); the AWS HTTP sink stays as an adapter in a module of its own (ADR-008).
- It says what did not change: no environment is read (ADR-004), a failing sink never fails the caller (ADR-005), masking before every sink (ADR-006).
- Open question to the maintainer: where does the note live, in the README, in a document of its own under `docs/`, or in both? Proposed: one short section in `docs/deployment/deployment.md`, linked from the README.
- It must not name the consumer project or any internal host (public repository).
