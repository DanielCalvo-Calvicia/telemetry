## Goal

After every epic, make the documents say what is true: architecture, API, configuration, requirements, security, monitoring, deployment, the README and the docs index. Each task already updates its own documents; this pass catches what a task missed and the drift between documents.

## Design notes

- Recurring: the task is not closed. After each epic a pass is made and its date is added to the epic and to the board; the task stays `todo` until the last epic (T-12) has had its pass.
- The checks of one pass: the table of the repository rules (`CLAUDE.md`, "every change updates the documentation") against the changes of the epic; the layout of the README and of `docs/architecture/architecture.md` against `git ls-files`; `go doc` of every exported identifier (each starts with its own name) and the Python docstrings; the requirement rows and the status table against the registry (`contracts/capabilities/registry.yaml`); the configuration document against the tags of `Config` and `.env.example`.
- What is planned is marked planned and what is built is marked built; nothing is described as working when it is not (CLAUDE.md, rule 3). ADRs are history, so they get dated notes, not rewrites.
- The check of links is mechanical: every relative link in `docs/` and `README.md` resolves, including anchors.
- A false statement found in a pass is fixed in the document and, if it came from a task, the task is corrected too.
- The public-repository rules apply to every edit: placeholders only, no internal host, no secret.

## Files

- `README.md`, `docs/README.md`
- `docs/architecture/architecture.md`, `docs/api/api.md`, `docs/configuration/environment-variables.md`, `docs/requirements/requirements.md`
- `docs/security/security.md`, `docs/operations/monitoring.md`, `docs/deployment/deployment.md`
- `.env.example` and `docs/decisions/` (new ADRs or dated notes, with their rows in the indexes)
- the board and order of `docs/tasks/README.md` and `docs/tasks/ORDER.md` (written by the coordinator of the plan, not by hand here)

## Documents updated in the same change

The pass is the change: the files above, plus the epic file of the epic that was just finished (its status and the date of the pass).

## Acceptance criteria

- After each epic, every document above agrees with the code and the contract as they are at that moment.
- No document describes a planned capability as built, and no built one as planned.
- The table of requirements and the status table of the README match the capabilities registry.
- Every link of the changed documents resolves.

## Verification

Run a link checker over `docs/` and `README.md`; run `go doc ./...` in the core module and compare with the API document; read the diff of the epic against the table of `CLAUDE.md` and tick each row.
