## Goal

Release the beta versions in the order of the release rule, with one tag per Go module and one for Python, and keep the table of releases, the README status and the install lines true. **A tag is permanent: only when the maintainer asks.**

## Design notes

- The rule of T-01.6 and REQ-VER-001: the core first (`go/vX.Y.Z`, the first one `go/v0.3.0`), then each adapter (`go/pkg/<functionality>/<adapter>/vX.Y.Z`) that pins a minimum core version, then Python (`python-vX.Y.Z`). `schema_version` starts at `0.1`.
- Each tag goes on `main` after the checks pass and the cross tests of T-12.1 are green (flow of ADR-010 and of `CLAUDE.md`: `feature_*`, then `feature`, then `main`). A tag is never moved or reused; a bad release gets a `retract` in the `go.mod` and a new patch version.
- Python is installed from Git, for example `pip install "telemetry[sqlite] @ git+https://github.com/DanielCalvo-Calvicia/telemetry@python-vX.Y.Z#subdirectory=python"`; nothing is published to an index (REQ-DST-002).
- Before the first tag of each module the `go.mod` does not contain a `replace` that points to a local path, because `go.work` is for local work only.
- Open questions to the maintainer: the version of the first Python tag (PR-001 gives only the Go one) and which capabilities a first `0.x` includes (the build is one capability at a time, Q02-5). Every release of this task is requested by the maintainer one at a time; one approval does not cover the next.
- A release never says `1.0`; that is T-13.5.

## Files

- `docs/deployment/deployment.md` (the table of releases, the install lines, the rollback and `retract` text)
- `README.md` (the status table and the `go get` and `pip install` lines of the quick start)
- `go/go.mod` and `go/pkg/<functionality>/<adapter>/go.mod` (the minimum core version of each adapter), `python/pyproject.toml` (the version)
- tests: the release rule is checked by a script under `integration-tests/release/` that reads the `go.mod` files and fails on a `replace` to a local path or a missing minimum core version, with fixtures under `integration-tests/release/fixtures/`

## Documents updated in the same change

`docs/deployment/deployment.md`, `README.md`, `docs/README.md` if a document is added, and the contract version line (`schema_version`) in `docs/api/api.md`.

## Acceptance criteria

- The check script passes for the core and every adapter before a tag is proposed to the maintainer.
- The table of releases lists each tag with its date and what it contains, only after the tag exists.
- The `go get` and `pip install` lines of the README name a tag that exists.
- No tag is created, moved or pushed without the maintainer's request in that session.
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

Run the release check script and the full checks of the README section 3 on `main`; after a tag, run `go get` of the module and `pip install` from Git in a clean directory.
