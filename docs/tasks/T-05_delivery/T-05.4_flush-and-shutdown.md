## Goal

Let the consumer empty the queues before the process ends: `flush` and `shutdown`, both with a timeout and both returning a result (REQ-DLV-010).

## Design notes

- There is no synchronous send mode, so the consumer must call `shutdown` before exiting, or events in the queues are lost (REQ-DLV-002). The documents and the doc comment say this in the first lines.
- `flush(timeout)` sends what is queued and keeps the library running; `shutdown(timeout)` does the same and then stops the workers. After shutdown a log call is dropped and counted, never an error.
- The result states how many events were sent, how many were left in the spool and how many were dropped (REQ-DLV-010). Before T-06 exists the spool count is always zero; the field is there from the start so the contract does not change later.
- Events still queued when the timeout ends are counted as dropped (or as left in the spool in `durable` mode, T-06.5); the call returns at the timeout, not later.
- It never throws or raises, also when a destination fails or hangs at shutdown (10.6, ADR-005). A failure appears in the result and in diagnostics.
- Per-destination detail in the result is wanted by T-05.5; the exact shape is shared with it.
- Question to the maintainer: does a second call to `shutdown` return the first result or an empty one? (The proposal is the first result, because it is the least surprising.)
- Python: no hidden hook at interpreter exit; the library is passive (1.2). A helper that registers one would be the consumer's choice, and is not planned.

## Acceptance criteria

- With a healthy destination `shutdown` returns all events as sent and exits before its timeout.
- With a hanging destination it returns at the timeout with the queued events counted as dropped.
- It does not throw in any of these cases, nor when called twice or before any event.
- The result has the three counts from the first release, with the spool at zero until T-06.

Ends with the checks of the README section 3 green in every language the task names.
