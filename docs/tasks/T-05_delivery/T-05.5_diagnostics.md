## Goal

Let the consumer see how delivery is doing, per destination, without a failure of the library creating events that fail again (REQ-DGN-001 to REQ-DGN-003).

## Design notes

- Per destination: queue depth, drops by reason, export failures, retries, export latency, batch size, spool use and quota, last successful send, configuration errors, serialization failures and the result of the last flush (REQ-DGN-001). Spool figures stay at zero until T-06.5.
- Two ways to read it (REQ-DGN-002): a snapshot function that returns a copy, and optional callbacks the consumer registers. A callback that fails or is slow must not break the worker; it runs outside the send path.
- An internal channel with its own rate limit, so a failure of telemetry never produces an event that goes through the normal path and can fail again (REQ-DGN-003). The rate limit value is not in PR-001: question to the maintainer.
- Open point for the maintainer: ADR-005 sends an ERROR entry to a fallback sink (the console) when a sink fails. Does the diagnostics channel replace that fallback, or does the console stay as a destination of the diagnostics?
- Diagnostics carry counters and identifiers, never the message or the fields of an event (they may be sensitive, ADR-005) and never a credential (REQ-SEC-007).
- The drop reasons are the ones of T-05.2 and the failure classes those of T-04.4; one list in `contracts/enums/` keeps the names equal in Go and Python (REQ-CNF-001).
- Diagnostics are not a health signal: a failing exporter does not mark the application unhealthy (REQ-HLT-003, T-07.4).

## Acceptance criteria

- A scenario with drops, failures, retries and a flush gives the expected value for each counter of REQ-DGN-001, in both languages.
- The snapshot is a copy: changing it does not change the library.
- A callback that raises or hangs does not affect delivery.
- A failing diagnostics callback produces no new telemetry event, and the channel's rate limit holds under a storm of failures.
- No diagnostic holds an event message, a field value or a token.

Ends with the checks of the README section 3 green in every language the task names.

## Verification

Tests with fake destinations that fail in each way; a test of the rate limit with a fake clock; a test that searches the snapshot and the callback payloads for a known secret and a known message and finds neither.

## Notes

**Done 2026-11-04** (Go 1.25.5, Python 3.11.1). The coordinator wrote the contract pieces (two enums, `drop_reason` and `diagnostic_code`, and the regenerated code) and the two shared fixtures (30 cases of the rate limit and 40 scenarios, from an independent Node model); two agents built the halves in parallel; the coordinator aligned two differences and verified. See section 2.29 of the architecture document.

- **Built.** The snapshot per destination (all the counters of REQ-DGN-001), the callbacks and a writer, the channel of its own with the pure rate limit (`PlanDiagnostic`) and a bounded queue of 64 read by one dispatcher, the cleaning of the reasons, `LastFlush` per destination, and the public names in both languages (`Diagnostics()` / `diagnostics()`, `WithDiagnosticsCallback` / `with_diagnostics_callback`, `WithDiagnosticsWriter` / `with_diagnostics_writer`).
- **Verification.** Both fixtures pass in both languages with no edit; Go coverage 98.2%, Python 1,034 tests at 100%; a differential test of 20,000 random inputs of the rate rule and 20,000 reasons of the cleaning (0 differences); mutating `>=` to `>` in the Go window rule made the shared test fail. Two differences found in the review and aligned: the rule of `last_success_at_ms` (it follows `delivered`: set only by the answer that ends a batch, a correction of the first text of the spec) and the cleaning of `last_reason` and the keys of `dropped_by_reason` in the public snapshot (Python did it, Go now does too). A flaky existing e2e test (`Test_new_builds_a_core_with_the_default_clock...`) reported `Sent:1` because it shut down while the delivery was still being counted; it now waits for the delivery in the diagnostics.
- **Open questions, decided with defaults and not asked.** The rate limit: 10 diagnostics per 1,000 ms in a fixed window, a queue of 64, constants and **no setting**; the diagnostics channel **replaces** the ADR-005 fallback entry (there was none in the new code) and the console can be the writer.
- **Known gaps.** The counts of events rejected by validation and the limits are not in the snapshot; the counters of the file destination are not either; a drop after `Shutdown` is counted but not published; Python publishes no shutdown drain because it drops nothing at the end; the spool figures are 0 until T-06.5; the rate limit is not a setting.
