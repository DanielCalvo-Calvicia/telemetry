## Goal

One test per row of the failure matrix of section 10.6 that this epic implements, in both languages, against the fake receiver, so the behavior of delivery is proved and not only described.

## Design notes

- Rows covered here: network down or timeout, HTTP 429 (with and without `Retry-After`), HTTP 5xx, HTTP 4xx except 408 and 429, invalid response, full queue, serialization failure and failure at shutdown.
- Rows of 10.6 that belong to other tasks and are linked, not repeated: invalid configuration (T-03.6), full disk quota and corrupted spool (T-06.5), invalid measurement (T-08.1, T-08.2). The matrix table in `contracts/capabilities/registry.yaml` maps each row to its test, so no row is left without one (REQ-CNF-007, T-02.7).
- Each test checks three things: what the caller saw (never an error, never a wait), what the destination received, and the counters of T-05.5.
- The tests use the fake receiver of T-04.8. This is not a listed dependency of the task; flagged for the coordinator, who may add T-04.8 to it.
- The cases are data (a fixture), so Go and Python run the same table with the same expected counters (REQ-CNF-005). The retry instants may differ between languages (section 13.1), so the tests assert the number of attempts and the final counters, not the exact delays.
- Serialization failure: an event whose attributes cannot be serialized is dropped and counted; the caller sees nothing and the other events in the batch are sent.
- Failure at shutdown: a hanging destination at `shutdown` gives a result with drops and no exception.

## Acceptance criteria

- Every row listed above has one test in Go and one in Python, driven by the same fixture.
- In every row the caller of the log call gets no error and is not delayed beyond the queue.
- The counters after each row equal the expected ones of the fixture.
- A second destination configured in the same run still receives its events while the first one fails.

Ends with the checks of the README section 3 green in every language the task names.
