## Goal

A log call enqueues the event and returns at once; a worker sends the events in batches to each destination (REQ-DLV-002, REQ-DLV-006).

## Design notes

- One bounded queue per destination, because the drop policy and the diagnostics are per destination (10.2, REQ-DGN-001). Question to the maintainer: or one shared queue with a cursor per destination?
- Defaults: queue 10,000 events, batch 100, flush every 2 s, network timeout 3 s; all configurable (REQ-DLV-006, Q03-4). A batch leaves when it holds 100 events or when the flush interval ends, whichever comes first.
- Go: a goroutine per destination. Python: a thread per destination that does not touch any event loop, so it also works inside an `asyncio` program (REQ-DLV-002, Q07-7). The Python API stays synchronous.
- Passivity (1.2): the worker starts only when the consumer builds and starts the library, never on import. No synchronous mode exists (Q03-6).
- A slow destination blocks only its own worker. The queue is the only thing the log call touches, so a call never waits for the network or the disk.
- The worker calls the destination with a timeout (REQ-DLV-004) and treats the result as a value (ADR-005). The retry and the modes are T-05.3; this task sends once and reports the result.
- Order of events inside one destination is kept.
- A configuration with a queue or a batch size of zero or less fails at start with the field and the reason (REQ-CFG-002).

## Acceptance criteria

- With a destination that never answers, 10,000 log calls return in a time that does not depend on the destination.
- A batch is sent at 100 events or after 2 s, with the defaults, and the order is kept.
- A destination that hangs does not delay a second destination.
- In Python the worker runs inside a program that uses `asyncio` and does not block its loop.
- Nothing starts before the consumer starts the library.

Ends with the checks of the README section 3 green in every language the task names.

## Verification

Tests with a fake clock and fake destinations (including one that blocks); a timing test of the log call against a blocked destination; a Python test that runs inside `asyncio.run`.

- **Changes that reach other tests.** Every test that expected a sink to have been called when `Emit` returned now waits for it (a helper `eventually` / `waiting.Eventually` that polls up to 5 s, plus a 30 ms wait to prove nothing extra arrives) and uses a flush of 5 ms; no assertion was weakened. The shared core fixture of the failing sink changed (accepted 2, failed 0).
- **Open questions, decided with defaults and not asked.** One queue per destination (the task asked for the maintainer's choice); the timeout of `timeout_ms` is passed to a sink in Go and **not** in Python (the port has no way; proposal: a keyword argument); the interval counts from the oldest waiting event; a full queue drops the new event (T-05.2 decides the policies).
- **Known gaps.** `Shutdown` is a stub, so the workers run until the process ends and a short program loses what is queued (the sample sleeps one second before it exits); the diagnostics are not public; no retry yet.
