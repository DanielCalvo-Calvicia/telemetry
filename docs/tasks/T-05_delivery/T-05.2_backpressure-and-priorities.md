## Goal

Decide what happens when a queue is full and which events matter most, and count every drop (REQ-DLV-007, REQ-DLV-008, REQ-DLV-009).

## Design notes

- Three policies per destination: `drop_newest` (the default), `drop_oldest` and `block_with_timeout`. The last one needs a timeout and is never the default; a configuration with it and no timeout fails at start (REQ-CFG-002).
- Three classes: `critical`, `normal`, `bulk`. When the queue is full, a `critical` event drops events of lower classes first and takes their place; `normal` and `bulk` follow the configured policy (10.3). The rule for a full spool is T-06.5, not this task.
- The class is assigned by `event_type` and the assignment is configurable. Open point for the maintainer: 10.3 puts logs at INFO or above in `normal` and DEBUG or TRACE in `bulk`, but both are the same event type, `log.entry.recorded`. Is the class chosen by event type and severity together? The proposal text says only by event type.
- Question to the maintainer: which class does an event type that is in no assignment get? (`normal` is proposed.)
- Priority is not a guarantee (REQ-DLV-009): the documents and the API doc comments say so.
- Every drop is counted per destination and reason (`queue_full_newest`, `queue_full_oldest`, `block_timeout`, `displaced_by_critical`, the final names are chosen with T-05.5). A drop never raises.
- A `block_with_timeout` call blocks the caller for at most its timeout; this is the one documented case where a call can wait, and the documents say so.

## Acceptance criteria

- Each policy gives the expected queue and the expected drop counter for every case of the fixture, in both languages.
- A `critical` event enters a full queue by displacing a lower-class event; if there is none, the configured policy applies.
- `block_with_timeout` without a timeout is a configuration error; it is not the default.
- Changing the class of an event type in the configuration changes where it is dropped.

Ends with the checks of the README section 3 green in every language the task names.

A difference found in the review: Python counted a drop a sink reports in the per-reason map and Go did not; Go was aligned (`unspecified` when the sink gives no reason).
- **Open questions, decided with defaults and not asked.** One policy for the whole core instead of one per destination (REQ-DLV-007 says *per destination*: **not met yet**, planned); the class of a log by severity as well as by type; `normal` for a type in no assignment; a `critical` event displaces the oldest `bulk` first, then the oldest `normal`; `drop_oldest` never displaces an event of a higher class; an empty queue policy is invalid.
- **Known gaps.** The counters are in the stats and not public (T-05.5); the spool rule for a full spool is T-06.5; the wait of `block_with_timeout` ends when the caller's context is cancelled (Go) and in Python uses the real clock, not the clock port.
