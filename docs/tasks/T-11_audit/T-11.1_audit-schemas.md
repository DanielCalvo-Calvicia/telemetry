## Goal

Write the JSON schemas of the `audit.*` event types in `contracts/schemas/`, so audit events are a typed contract in both languages from the start (Q06-6).

## Design notes

- Every `audit.*` event uses the envelope of T-02.2 and has its own `data` schema registered in `contracts/schemas/` (REQ-CTR-002). The enums and the error codes come from the generator (T-02.4); nothing is written by hand in Go or Python (REQ-CNF-001).
- PR-001 names only the family `audit.*` and does not list the event types or the fields. Nothing is invented here. Questions to the maintainer before the schemas are written:
  1. Which event types are in the first list (for example an access, a change of configuration, a decision of an agent)? If none is known, a single generic `audit.action.recorded` is the smallest start.
  2. Which fields does `data` hold (who did it is already the `actor` of the envelope; what, on which object, the outcome)?
  3. Are the `data` values subject to masking by field name like any other event (ADR-006)? The default list of REQ-SEC-002 applies unless the maintainer says otherwise.
- The new event types also join the list of event types and error codes of T-02.3, which is why the three questions are asked when the task starts.
- The schemas carry `schema_version` 0.1 like the rest (REQ-VER-001).

## Files

- `contracts/schemas/audit/` (one schema file per event type, named like the type)
- `contracts/enums/` only if a new enum is needed (for example the outcome)
- the generated code of both languages (`go/internal/domain/...` and `python/src/telemetry/internal/domain/...`), regenerated by the generator of T-02.4 and committed
- tests: `go/internal/tests/contract/` and `python/internal/tests/contract/` (a valid and an invalid example per type); fixtures under `integration-tests/fixtures/audit/`

## Documents updated in the same change

`docs/api/api.md` (the event types), `docs/requirements/requirements.md` (REQ-SEC-006), `docs/architecture/architecture.md`, `docs/security/security.md`, the status table of `README.md`, and a dated note in `docs/decisions/ADR-006-masking-before-every-sink.md` if a field name is added to the masking list.

## Acceptance criteria

- Each `audit.*` type has a schema in `contracts/schemas/` and appears in the registered list of event types.
- The valid example validates and the invalid one is rejected with the classified error code, in both languages.
- The generated code matches the contract (CI check of T-02.4).
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

The contract tests of both languages over the fixtures; the generator run that shows no difference with the committed code.
