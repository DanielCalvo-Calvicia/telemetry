## Goal

Make audit events a distinct type in the pipeline, and let a project route them to a destination of their own (REQ-SEC-006, REQ-OUT-003) without mixing them with diagnostic logs.

## Design notes

- Routing works by event family. An `audit.*` event goes only to the destinations the consumer attached to audit, and a destination attached to logs does not receive it unless the consumer attached it to audit too (REQ-OUT-003: sharing a destination between capabilities is an explicit configuration decision).
- Masking happens before any sink, audit included (ADR-006); there is no unmasked path (CLAUDE.md).
- The priority of audit events in the queue comes from T-05.2. Open question to the maintainer: is an audit event dropped like a log when the queue is full, or does it have the highest priority and never drop before the lowest ones? PR-001 section 10.3 sets the priorities; only the maintainer may say that audit changes them.
- Open question to the maintainer: does audit get its own outbound port `AuditSinkPort` (PR-001 section 3.1 has an `outbound/audit/` folder but section 7.1 lists no such port) or does it use the generic event port `EventSinkPort`?
- A sink that fails never fails the caller (ADR-005), and audit has no exception: the failure is counted in diagnostics. The warning of T-11.3 says what that means for the project.
- The destination is chosen in code by importing it and passing it to the core (REQ-ARC-013); the configuration carries no adapter name.

## Acceptance criteria

- With a console destination attached to logs and a file destination attached to audit, an audit event reaches only the file and a log only the console.
- With no audit destination attached, an audit event is counted in diagnostics and goes nowhere; it is not sent to the log destinations.
- Audit events pass through masking before the sink.
- Ends with the checks of the README section 3 green in every language the task names.
