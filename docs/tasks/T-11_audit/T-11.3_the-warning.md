## Goal

State in the documents, where a consumer will read it, that HTTP and files do not guarantee immutability or legal retention, so nobody uses `audit.*` as a legal record by mistake (REQ-SEC-006, section 1.3 of PR-001).

## Design notes

- The text says what the library gives (a separate type, a separate route, masking, the delivery modes) and what it does not give: immutability, tamper evidence, ordering across processes, retention, deletion rules, and delivery in every case (a destination that fails is counted in diagnostics and the event can be lost in the modes `best_effort` and `retry`).
- It names what the SQLite file adds and does not add: it is durable on the machine, but the writer can delete rows and a reader cannot prove they were not edited.
- It points to the project as the one that owns the policy: where audit goes, how long it is kept and who may read it (the library is passive).
- It must stay true with what T-11.2 built; if T-11.2 changes the routing or the priority of audit events, the text follows.
- One short warning, written once in the security document and linked from the others; no copy of the paragraph in several files.

## Files

- `docs/api/api.md` (a one-line pointer where the `audit.*` types are listed)
- `README.md` (a pointer in the capability list or the status table)

The four files above are the change. In addition `docs/operations/monitoring.md` if the diagnostics of a failing audit destination are described there, and the checklist of `docs/security/security.md` gets a line "audit events are not used as a legal record".

## Acceptance criteria

- The security document says in plain words that HTTP and files do not guarantee immutability or legal retention.
- It lists what the library gives and what it does not give, and names the project as owner of the policy.
- The API document and the README link to that section instead of repeating it.
- What is planned (the audit adapter) is marked planned, not working.
- Every link of the changed documents resolves.
