## Goal

Write the rule of how versions and tags work for the new layout, before the first tag is needed.

## Design notes

- REQ-VER-001 and Q06-8 (one tag per language): `go/vX.Y.Z` for the core module, `go/pkg/<functionality>/<adapter>/vX.Y.Z` for each adapter module, `python-vX.Y.Z` for the package; `schema_version` versions the contract on its own, starts at `0.1` and reaches `1.0` with the library.
- ADR-013 and Q09-3: each adapter pins a minimum core version, and the core is released first. `go.work` serves local work and CI only; a released adapter must build without it.
- Q07-2: the first core tag is `go/v0.3.0`. The old path `github.com/DanielCalvo-Calvicia/telemetry` keeps `v0.1.0` and `v0.2.0` and is never moved.
- Q09-6 and REQ-CNF-008: the library stays `0.x` (a beta) until every capability works; `1.0` is the maintainer's decision (T-13.5).
- Rules already in `CLAUDE.md` that the text repeats: a tag is permanent and never moved or reused; a bad release gets a `retract` and a new patch version; the flow is `feature_*`, then `feature`, then `main`, with the tag on `main` after the checks pass; nothing is tagged unless the maintainer asks (ADR-010).
- Open for the maintainer: whether a contract change that adds an optional field (MINOR of `schema_version`, REQ-VER-003) forces a release of both languages. Write it as a question; do not choose.
- This task writes text only; no tag is created.
