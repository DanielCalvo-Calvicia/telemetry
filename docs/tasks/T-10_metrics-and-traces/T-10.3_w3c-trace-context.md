## Goal

Propagate the trace over HTTP with the W3C Trace Context headers, so a Go service and a Python process correlate in one trace, and never treat an incoming context as authorization.

## Design notes

- Two operations in each language: inject the current context into outgoing headers (`traceparent`, and `tracestate` when present) and extract it from incoming ones to start a child span (REQ-TRC-002). The library owns no HTTP server or client; it works on a plain map of headers and the project, or an adapter, does the HTTP.
- Validation (REQ-TRC-003): a `traceparent` that is malformed, has an unknown version, an all-zero trace id or span id, or is too long is ignored and a new trace starts; the event is counted in diagnostics and never raised to the caller.
- An incoming context only sets correlation ids. No code path may read a role, a permission or a tenant from it, and the documents say so.
- `tracestate` is carried as received and not interpreted. Open question to the maintainer: is `tracestate` needed in the first pass, or only `traceparent`? The sampled flag is carried, but nothing samples (see the epic).
- The pure parsing, formatting and validation live in the domain and are shared by the inject and extract services.

## Acceptance criteria

- Inject then extract returns the same trace id, a new span id and the parent link.
- Every invalid case of the fixture starts a new trace and is counted; none raises.
- The same fixture file gives the same result in Go and Python.
- The security document says an incoming context is never authorization.
- Ends with the checks of the README section 3 green in every language the task names.

## Verification

Table-driven tests over the shared fixture of valid and invalid headers in both languages; a test that no function of the library returns an identity or a permission from a trace context.
