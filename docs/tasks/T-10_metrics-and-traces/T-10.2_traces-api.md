## Goal

Let a project start and end spans with parent and child relations, an error state and a duration, and let the other capabilities read the current `trace_id` and `span_id` from the call context.

## Design notes

- A span has a name, a trace id, a span id, an optional parent, start and end instants taken from `ClockPort`, a status (`ok` or `error`) and flat scalar attributes (REQ-CTR-010). Ids come from `IDGeneratorPort`; their format is the W3C one fixed in T-10.3 (16-byte trace id, 8-byte span id), not a UUIDv7.
- Spans go to a new outbound port `TraceSinkPort`; without a sink they are cheap and do nothing. Open question to the maintainer, the same as in T-10.1: does a span also produce a `trace.*` event for the event destinations (Q02-5 lists the family), or does it only reach `TraceSinkPort`?
- The current span lives in the call context of T-03.8. Once it exists, logs, executions and faults attach `trace_id` and `span_id` (REQ-LOG-005); the logger of T-04.1 reads them from the context, so this task only has to fill them.
- Ending a span twice, or ending a child after its parent, is not an error for the caller (ADR-005): the second end is ignored and counted in diagnostics.
- Span attributes pass through masking before any sink (ADR-006).

## Acceptance criteria

- A span records its start, end, duration and status; a child shares the trace id of its parent and has its own span id.
- An error status is kept when the span ends.
- A log recorded inside a span carries its `trace_id` and `span_id`.
- A double end and an end out of order never fail the caller.
- Ends with the checks of the README section 3 green in every language the task names.
